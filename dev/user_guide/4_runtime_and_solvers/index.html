Runtime and solvers

Final steps before launching a simulation

Runtime setup

At this stage in the setup workflow, the user defines the runtime information to configure the runtime behaviour of the flow solver, including the time step to use (only meaningful for transient solutions), as well as information about how often to write results to disk. XCALibre.jl provides a the Runtime to perform this operation.

XCALibre.Solve.Runtime — Type
Runtime(; 
        # keyword arguments

        iterations::I, 
        write_interval::I, 
        time_step::N,
        adaptive::A
    ) where {I<:Integer,N<:Number} = begin
    
    # returned Runtime struct
    Runtime{I<:Integer,F<:AbstractFloat}
        (
            iterations=iterations, 
            dt=time_step, 
            write_interval=write_interval,
            adaptive=adaptive
        )
end

This is a convenience function to set the top-level runtime information. The inputs are all keyword arguments and provide basic information to flow solvers just before running a simulation.

Input arguments

  • iterations::Integer: specifies the number of iterations in a simulation run.
  • write_interval::Integer: defines how often simulation results are written to file (on the current working directory). The interval is currently based on number of iterations. Set to -1 to run without writing results to file.
  • time_step::AbstractFloat: the time step to use in the simulation. Notice that for steady solvers this is simply a counter and it is recommended to simply use 1.
  • adaptive::Union{Nothing, AdaptiveTimeStepping}: optionally enables adaptive time stepping. Pass an AdaptiveTimeStepping object to automatically adjust dt based on the Courant number during transient simulations. Defaults to nothing, meaning a fixed time step is used.

Example

runtime = Runtime(iterations=2000, time_step=1, write_interval=2000)

Configuration object

Once all the simulation configuration information has been defined, from discretisation scheme to runtime information, all settings must be wrapped in a Configuration object. The definition, including expected input arguments, for the Configuration object are detailed below.

XCALibre.Simulate.Configuration — Type
struct Configuration{SC,SL,RT,HW,PP}
    schemes::SC
    solvers::SL
    runtime::RT
    hardware::HW
    postprocess::PP
end

The Configuration type is passed to all flow solvers and provides all the relevant information to run a simulation.

Inputs

  • schemes::NamedTuple this keyword argument is used to pass distretisation scheme information to flow solvers. See Numerical setup for details.
  • solvers::NamedTuple this keyword argument is used to pass the configurations for the linear solvers for each field information to flow solvers. See Runtime and solvers for details.
  • runtime::NamedTuple this keyword argument is used to pass runtime information to the flow solvers. See Runtime and solvers for details.
  • hardware::NamedTuple this keyword argument is used to pass the hardware configuration and backend settings to the flow solvers. See Pre-processing for details.

Optional keywords

  • postprocess this keyword argument is used to pass any fields that need to be post-processed. See Post-processing for details.

Example

config = Configuration(
    solvers=solvers, schemes=schemes, runtime=runtime, hardware=hardware, boundaries=BCs)

Initialising fields

The last (optional) step before running the simulation is to provide an initial guess for all the fields being solved. Although this step is optional, in most cases the flow solvers will perform better when initialised. To set an initial value for a field, the initialise! function is provided, which assigns a starting value to a given field.

XCALibre.Fields.initialise! — Function
function initialise!(field, value) # dummy function for documentation
    # Assign `value` to field in-place
    nothing
end

This function will set the given field to the value provided in-place. Useful for initialising fields prior to running a simulation.

Input arguments

  • field specifies the field to be initialised. The field must be either a AbractScalarField or AbstractVectorField
  • value defines the value to be set. This should be a scalar or vector (3 components) depending on the field to be modified e.g. for an AbstractVectorField we can specify as value=[10,0,0]

Note: in most cases the fields to be modified are stored within a physics model i.e. a Physics object. Thus, the argument value must fully qualify the model. For example, if we have created a Physics model named mymodel to set the velocity field, U, we would set the argument field to mymodel.momentum.U. See the example below.

Example

initialise!(mymodel.momentum.U, [2.5, 0, 0])
initialise!(mymodel.momentum.p, 1.25)

initialise! also accepts a functions arguments and initialises a field by evaluating the function at each cell centre. The function should have the signature f(x, y, z) and it must return either a scalar or an SVector type (requirement to work on GPUs)

source

A uniform initial guess leaves a velocity field that does not satisfy continuity, which the first few solver iterations must work off before making physical progress. For external and internal flows around bodies, a potential-flow field is a much better starting point: it already satisfies continuity and carries the shape of the geometry.

potential_flow! solves a velocity-potential equation on the current mesh and sets the velocity to the resulting divergence-free field. By default it starts from rest: the internal velocity is set to zero first, so the flow is driven by the velocity boundary conditions alone (pass from_rest=false to project the current field instead). Boundary conditions for the potential are inferred from those already assigned to pressure, so no extra setup is needed.

XCALibre.Solvers.potential_flow! — Function
potential_flow!(model, config; ncorrectors=0, pref=nothing, time=0, petsc_options="", from_rest=true)

Set the velocity to a divergence-free potential-flow field. With from_rest=true (default) the internal velocity is first set to zero, so the face flux to be corrected comes from the velocity boundary conditions only; with from_rest=false the current velocity field is projected. A nonzero initial field that is not a discrete gradient (a uniform field on a non-orthogonal mesh, for instance) keeps a solenoidal part after the projection, which shows up as spurious circulation, notably in enclosed or near-stagnant regions. Velocity-potential boundary conditions are inferred from pressure: fixed pressure becomes fixed zero potential, periodic patches remain periodic, and other patches use zero normal gradient.

The corrected face-volume flux is returned with the residual of the last potential solve, taken before that solve.

source

Call it after initialise! and before run!:

initialise!(model.momentum.U, velocity)
initialise!(model.momentum.p, 0.0)

potential_flow!(model, config; ncorrectors=5)

residuals = run!(model, config)

On meshes with appreciable non-orthogonality, pass ncorrectors to run non-orthogonal correctors on the potential equation. Set it to zero for orthogonal meshes.

AMG preconditioner

Algebraic multigrid is a preconditioner: solver picks the outer iteration and preconditioner = AMG(...) the multigrid. Use solver = Cg() for symmetric systems such as incompressible pressure, solver = Bicgstab() for non-symmetric ones (compressible pressure, momentum, scalars) and solver = Richardson() for plain V-cycles with no Krylov acceleration.

SolverSetup(
    solver = Cg(),
    preconditioner = AMG(),
    convergence = 1e-7,
    relax = 1.0,
    rtol = 0.0,
    atol = 1e-5
)

AMG(coarsening; smoother, sweeps, coarsest, refresh, native):

  • coarsening: how cells are grouped into coarse levels.
    • Pairwise(merges=1) (default): each cell is paired with the neighbour it is most strongly coupled to, merges times per level. Piecewise-constant transfer between levels. Cheap to build, light on memory and robust for non-symmetric matrices.
    • SmoothedAggregation(; threshold=0.0): larger aggregates with a smoothed interpolation; fewer iterations on hard symmetric problems at a higher setup and memory cost.
    • RugeStuben(; threshold=0.25): classical AMG, serial meshes only (on a distributed mesh use BoomerAMG()).
  • smoother: Jacobi() (default), Chebyshev(; degree=3), and on the CPU GaussSeidel(), SymGaussSeidel(), SOR(ω), SSOR(ω). Jacobi(weight=4/3) relaxes each level by weight/λmax, with λmax the largest eigenvalue of D⁻¹A there; SOR and SSOR take the relaxation factor ω directly.
  • sweeps: smoother sweeps before and after the coarse correction on each level. sweeps = 2 means two before and two after, sweeps = (0, 2) none before and two after, and Sweeps(pre, post; grow, max) adds grow sweeps per level down to at most max; more sweeps on coarse levels, where they are cheap, strengthen the cycle at little cost. Defaults to 2 for Jacobi() and 1 otherwise.
  • coarsest = 4096: coarsening stops once a level has at most this many rows.
  • refresh = 5: the coarse levels are recomputed from the current matrix every refresh solves. The aggregates and interpolation are kept while the sparsity pattern is unchanged; natively the finest level always uses the current matrix. Use refresh = 1 to recompute every solve.
  • native = NativeAMG(...): settings of XCALibre's own AMG, which a distributed mesh does not use (below).

SolverSetup(precision = MixedF32()) keeps the outer iteration and finest level in the equation's precision and stores the coarse levels in Float32, about halving the hierarchy's memory.

SolverSetup(
    solver = Bicgstab(),
    preconditioner = AMG(SmoothedAggregation(); smoother = SymGaussSeidel(), sweeps = (0, 2)),
    convergence = 1e-7,
    relax = 1.0,
    rtol = 0.0,
    atol = 1e-5
)

Cg() rejects a non-symmetric matrix. A typical non-symmetric case is the pressure equation in compressible flow, where the implicit pressure convection is upwinded; examples/2D_cylinder_transonic_RANS_AMG_BICGStab.jl solves it with Bicgstab() and AMG. If Bicgstab() breaks down (the shadow residual going orthogonal, or the stabilising step collapsing) the half-step iterate is kept and the solve restarts with a fresh shadow residual, at most twice. Cg() switches to its flexible form when the V-cycle is not symmetric (scale_correction, unequal pre and post, or a forward-only smoother), which tolerates the non-symmetric preconditioner; a symmetric V-cycle remains the better partner for Cg().

Earlier spellings

Earlier keywords and types still work for now, each with a one-time deprecation warning naming the current spelling: AMG(coarsening=..., pre_sweeps=..., coarse_refresh_interval=..., max_coarse_rows=..., coarse_solve=..., scale_correction=..., fuse_levels=...), Geometric(), SmoothAggregation(), AMGJacobi(), AMGChebyshev(), AMGGaussSeidel(), AMGSOR() and the OnDevice*/OnHost coarse solves. SolverSetup(solver = AMG(mode = Cg())) becomes solver = Cg(), preconditioner = AMG(...), AMGSolver() is Richardson(), and GAMG() returns the AMG() of PETSc's GAMG defaults. AMG(coarse_storage = Float32) is now precision = MixedF32().

Native settings

NativeAMG(; coarse=Direct(), scale_correction=true, fuse=0):

  • coarse: the coarsest-level solve, visited on every V-cycle.
    • Direct(; max_rows=512) (default): exact solve. On a GPU the factor stays on the device while the coarsest level has at most max_rows rows, otherwise it is solved on the host; max_rows = 0 always uses the host.
    • Smoothed(smoother=Chebyshev(degree=10); sweeps=1): fixed sweeps of Jacobi() or Chebyshev() on the device, a fixed linear operator valid with Cg(). Suits a large coarsest on a GPU.
    • Iterative(solver=Bicgstab(); rtol=1e-2, itmax=50): a Jacobi-preconditioned Krylov solve on the device. It depends on the right-hand side, so it needs solver = Richardson().
    • On a CPU backend every choice is a Direct() solve.
  • scale_correction: scales each coarse correction by (r·c)/(c·Ac), the factor that minimises the error in the energy norm.
  • fuse: on a GPU with Pairwise(), Jacobi() and Direct(), fuse = 1 keeps the transfers between levels as aggregate lists instead of sparse matrices (less memory, no extra work), and fuse = n > 1 also applies the top n - 1 coarse levels through the finer matrix instead of storing them, at the cost of extra matrix products per V-cycle; worthwhile when the hierarchy does not fit on the device. A CPU ignores it.
SolverSetup(solver = Richardson(), preconditioner = AMG(coarsest = 8000,
    native = NativeAMG(coarse = Smoothed(Chebyshev(degree = 8)))), convergence = 1e-7, relax = 1.0)

AMG on a distributed mesh

On a distributed mesh AMG(...) runs as PETSc's GAMG with its settings translated:

  • Pairwise() → -pc_gamg_agg_nsmooths 0 (unsmoothed aggregation); SmoothedAggregation(; threshold) → -pc_gamg_agg_nsmooths 1 -pc_gamg_threshold <threshold>. Aggressive coarsening is off (-pc_gamg_aggressive_coarsening 0) to mirror the native levels.
  • Jacobi(; weight) → Richardson with Jacobi and scale weight/2; Chebyshev(; degree, eig_ratio, lambda_scale) → PETSc's Chebyshev with Jacobi, degree as -mg_levels_ksp_max_it, bounds as -mg_levels_ksp_chebyshev_esteig; GaussSeidel(), SymGaussSeidel() → PETSc's SOR within each rank.
  • sweeps → -mg_levels_ksp_max_it, with a separate up smoother (-pc_mg_distinct_smoothup) when pre ≠ post.
  • coarsest → -pc_gamg_coarse_eq_limit; refresh = N → the preconditioner is held for N solves and its coarse operators recomputed on the next, keeping the interpolation (-pc_gamg_reuse_interpolation).
  • With any outer iteration other than Cg() the aggregation graph is symmetrised (-pc_gamg_graph_symmetrize), so non-symmetric matrices are supported.

What differs from the native AMG:

  • GAMG builds its aggregates with its own (MIS) algorithm, not pairwise, so hierarchies and iteration counts are close, not identical.
  • Jacobi() damps each level by weight/λmax natively; PETSc uses one scale, weight/2, exact for λmax ≈ 2.
  • Between refreshes PETSc applies the whole stored preconditioner, while the native AMG updates its finest level every solve.
  • NativeAMG settings are not used; when they differ from the defaults one info message lists them.

Settings GAMG cannot express stop the run: RugeStuben() (use BoomerAMG()), Pairwise(merges > 1), Sweeps(grow > 0), Chebyshev() with more than one sweep, SOR/SSOR with ω ≠ 1, and SmoothedAggregation(weight, near_nullspace).

The rules for every preconditioner are listed in the preconditioners section of the numerical setup page.

Launching flow solvers

In XCALibre.jl the run! function is used to start a simulation, which will dispatch to the appropriate flow solver for execution. Once the simulation is complete a NamedTuple containing residual information is returned for users to explore the convergence history of the simulation.

The residual of each field is the normalised residual Σᵢ|bᵢ - (Ax)ᵢ| / Σᵢ|Aᵢᵢxᵢ| of its assembled system, evaluated on the current field x just before the linear solve, so it measures how far the previous iteration's fields are from satisfying this iteration's equations. It does not depend on the linear solver, its preconditioner, precision or tolerances, nor on whether the run is serial, distributed or on a GPU. When the field is zero everywhere (a common initial pressure), the denominator is zero and the unnormalised Σᵢ|bᵢ - (Ax)ᵢ| is reported for that iteration.

XCALibre.Solvers.run! — Method
function run!(
    model::Physics, config; 
    output=VTK(), pref=nothing, ncorrectors=0, inner_loops=0, progress=true
    )

    # here an internal function is used for solver dispatch
    return residuals
end

This is the top level API function to initiate a simulation. It uses the user-provided model defined as a Physics object to dispatch to the appropriate solver.

Dispatched flow solvers

  • Steady incompressible (SIMPLE algorithm for coupling)
  • Transient incompressible (PISO algorithm for coupling)
  • Steady weakly compressible (SIMPLE algorithm for coupling)
  • Transient weakly compressible (PISO algorithm for coupling)

On a distributed mesh only the incompressible SIMPLE and PISO solvers, the Laplace solver and the density-based solver (SupersonicFlow) are supported; any other solver or model errors rather than solving each rank's block on its own.

Calling run! again on the same model continues from its current fields, including the face mass flux of the last iteration, and retraces the uninterrupted run. Re-initialising the fields (e.g. with initialise!) between calls starts afresh.

Input arguments

  • model reference to a Physics model defined by the user.
  • config Configuration structure defined by the user with solvers, schemes, runtime and hardware structures configuration details.
  • output select the format used for simulation results from VTK() or OpenFOAM() (default = VTK())
  • pref Reference pressure value for cases that do not have a pressure defining BC. Incompressible solvers only (default = nothing)
  • ncorrectors number of non-orthogonality correction loops (default = 0)
  • inner_loops number to inner loops used in transient solver based on PISO algorithm (default = 0)
  • progress show a progress bar with the iteration and residuals (default = true). Use progress=false for large-scale runs that are not on a local PC, e.g. cluster batch jobs. Distributed runs never show it
  • transpose_stress include the explicit part of the viscous stress, ∇·(μ_eff dev2((∇U)ᵀ)), in the momentum equation of the incompressible, compressible and multiphase solvers (default = true). It is zero for a constant viscosity in incompressible flow and needed wherever the effective viscosity varies, e.g. with a turbulence model; false drops it
  • consistent steady solvers (simple! and csimple!) only: use the consistent (SIMPLEC) pressure–velocity coupling, which needs little or no pressure under-relaxation and keeps steady transonic runs stable for common relaxation factors; see simple! and csimple! (default = false)
  • restart resume an incompressible run on a distributed mesh from results it wrote with output=OpenFOAM(): the iteration (steady) or time (transient) of a written time directory, or that directory's name. The resumed run continues from that point up to iterations and retraces the uninterrupted run (default = nothing)

Output

This function returns a NamedTuple for accessing the residuals (e.g. residuals.Ux). The fields available within the returned residuals tuple depend on the solver used. For example, for an incompressible solver, a x-momentum equation residual can be retrieved accessing the Ux field i.e. residuals.Ux. Look at reference guide for each dispatch method to find out which fields are available.

Example

residuals = run!(model, config) 

# to access the pressure residual

residuals.p
source

run! shows a progress bar with the current iteration and residuals. Pass progress=false to turn it off:

residuals = run!(model, config; progress=false)

We recommend progress=false for large-scale runs that are not on a local PC, such as batch jobs on a cluster, where the progress bar only fills the job's log. The residual history returned by run! is the same either way.

The momentum equation of every flow solver carries the full viscous stress, ∇·τ with τ = μeff (∇U + (∇U)ᵀ - ⅔ (∇·U) I). The part ∇·(μeff ∇U) is discretised implicitly as a Laplacian, and the rest, ∇·(μeff dev2((∇U)ᵀ)) with dev2(A) = A - ⅔ tr(A) I, is added as an explicit source evaluated from the current velocity gradient. For a constant viscosity in incompressible flow this source is zero, since ∇·(∇U)ᵀ = ∇(∇·U); it matters wherever the effective viscosity varies, as it does with any turbulence model. At boundary faces the source uses the owner-cell gradient with its normal derivative taken from the velocity condition: (Ub − Uc)/δ for fixed values (Wall, Dirichlet, RotatingWall, and DirichletFunction evaluated at the face and the current time), zero for Zerogradient, Extrapolated, Outlet and NeumannFunction, and the mirrored value for Slip and Symmetry; periodic faces are treated as internal faces between the two cells of a pair. Pass `transposestress=false` to leave it out, e.g. to compare with results obtained before it was included:

residuals = run!(model, config; transpose_stress=false)

The steady solvers (simple! for Incompressible fluids and csimple! for Compressible and WeaklyCompressible fluids, used by run! for Steady() models) offer a consistent (SIMPLEC) pressure–velocity coupling. By default, the pressure equation and the velocity correction use rD = V/aP, the inverse diagonal coefficient of the under-relaxed momentum matrix. Because aP grows as the velocity relaxation factor αU decreases, rD scales roughly with αU, so the pressure correction is over-damped and has to be compensated by pressure under-relaxation. With consistent=true the pressure Laplacian and the velocity and face-flux corrections use rDt = V/(aP + Σ aN), the inverse row sum of the momentum matrix, which does not shrink with αU; the extra terms (rDt - rD)∇p are added to the predicted velocity and face fluxes, so the converged solution is the same. Incompressible runs then need little or no pressure under-relaxation. In compressible flow the weak Laplacian of the default coupling also loses weight against the compressibility term ∇·(ψ ((H/aP)·S) p) of a Compressible fluid; in transonic flow this can amplify round-off from one iteration to the next until the run diverges, even for a uniform free stream on some meshes. The consistent coupling keeps the Laplacian's weight and is worth trying when a steady transonic run diverges. The option works on distributed meshes with simple!:

residuals = run!(model, config; consistent=true)

It is off by default, which leaves earlier results unchanged. The transient solvers do not take this option.

Restarting simulations

It should be noted that when running a simulation with run!, the solution fields in the Physics model are mutated. Thus, running the simulation from the previous solution is simply a matter of reissuing the run! function. The continued run also picks up the face mass flux of the last iteration, so a run split into several run! calls (for example, to monitor forces every few hundred iterations) retraces the uninterrupted run. Re-initialising the fields with initialise! between calls starts afresh. At present, this has the side effect of overwriting any existing solution files (.vtk or .vtu). Users must be aware of this behaviour.

In some cases, it may be desirable to solve a problem with a steady solver and use the solution to run transient simulations. This is possible using the change function.
